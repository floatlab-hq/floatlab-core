# FloatLab command contract

These modules mirror `api/openapi/*.yaml`. `manifest.json` lists them in assembly order; `cli.json` describes local utilities. A module is `{ "commands": [...] }` containing OpenCLI command objects. Modules are repository fragments, not independently published OpenCLI documents, and do not use `$ref`.

Run from the repository root:

```sh
pnpm commands:generate
pnpm commands:check
pnpm commands:coverage
```

Generation writes canonical API commands into each module, the assembled document to `packages/floatlab-client/src/commands.generated.json`, and the five shell scripts to `cli/completions/`. Commit both sources and generated files. CI checks freshness. Both CLI and browser import the assembled document; installed users need only the compiled `lab` binary. `lab install-autocomplete [bash|fish|ps1|nu]` installs its bundled script into shell configuration; releases do not ship a separate completion archive.

Every HTTP operation in `api/openapi/openapi.yaml` is available as `lab api <module> <operationId>` and as `api <module> <operationId>` in the command palette. Existing shorthand commands remain available. Inline root operations use the `openapi` module. `daemon.yaml` and `zfs.yaml` describe separate local Unix-socket services and are outside the management HTTP document.

Canonical commands expose every OpenAPI parameter as a value-taking option prefixed by its location, such as `--path-id`, `--query-limit`, or `--header-idempotency-key`. Boolean options take `true` or `false`. `--body` forwards the complete request body; JSON media take JSON text, binary media take base64, and text media take literal text. Required path parameters are required options. Required bodies must be supplied with `--body` or CLI-only `--body-file <path>`. These options are mutually exclusive; files provide raw bytes and avoid argument-size limits for binary archives. The command palette accepts `--body`. Idempotency keys can be supplied explicitly or generated by the runtime. Multiple body/response media types expose `--content-type`/`--accept` choices. The default media is the first declared type.

For example, `lab api stacks getStack --path-id stack-id` invokes the matching HTTP operation without resource-name resolution. Use `lab api stacks getStack --help` to inspect its inputs. API fragments are generated from fully resolved OpenAPI schemas; edit OpenAPI and rerun generation to change them.

Domain commands live with their primary API operation. Cross-domain workflows reference other modules' operation IDs. To split a group across modules, repeat the same group properties and contribute distinct children. Assembly rejects conflicting properties, duplicate executable commands, and colliding names or aliases.

## FloatLab metadata

All extensions use OpenCLI's standard `metadata: [{ "name": "floatlab", "value": { ... } }]` shape:

| Property | Purpose |
|---|---|
| `provider` | Suggestion provider: `stacks`, `nodes`, `containers`, `images`, `alerts`, `active-alerts`, `rules`, or CLI-only `files` |
| `dependsOn` | Argument supplying the resource scope, such as `stack` for containers |
| `suggestions` | Suggested examples without restricting accepted input |
| `appendSpace` | Continue with the next word when a candidate is accepted |
| `prompt` | Allow a required argument to be omitted in interactive mode; the existing handler gathers it |
| `defaultCommand` | Child selected when a group is invoked without arguments |
| `passthrough` | Preserve words after `--`; `exec` requires this delimiter |
| `capability` | Restrict suggestions to `cli`, `files`, or `interactive` contexts |
| `utility` | Local command handled by the CLI rather than an API workflow |
| `api` | Operation and request-input coverage declarations |
| `http` | Canonical transport: method, path, parameters with original names and explicit option bindings, request-body media/schema, authentication requirement, and default response media |

The parser validates command-specific flags, required inputs, choices, and arity. Existing handlers retain JSON/content validation, conditional option rules, confirmations, and API orchestration. Only use `acceptedValues` for actual constraints; put examples such as mute durations in `suggestions`.

## API mappings and report

For example:

```json
{
  "name": "floatlab",
  "value": {
    "api": [{
      "operationId": "deleteStack",
      "inputs": {
        "path/id": "argument:stack",
        "query/purge": "option:--purge",
        "header/Idempotency-Key": "runtime:idempotency"
      }
    }]
  }
}
```

Input keys are `path/name`, `query/name`, `header/name`, or `body/field/nested-field`. Body arrays and maps use `*` segments. Parameter names retain OpenAPI casing. Sources use `argument:`, `option:`, `json:`, `editor:`, `derived:`, or `runtime:`. Argument/option/JSON sources must reference a declared input; derived/runtime/editor sources describe existing handler behavior. Map only fields that handlers actually accept. A parent body mapping includes its descendants, appropriate for unrestricted JSON or Compose inputs.

Legacy workflow mappings may retain an `exclusion` explanation. Exclusions do not satisfy canonical API coverage. Every operation must have its canonical command, and every request input must have an exposed mapping. New fields beneath a broad body mapping are forwarded by the canonical handler; restrict shorthand mappings to individual fields when their handlers use an allowlist.

`commands:coverage` resolves the complete OpenAPI document and writes `dist/command-coverage/coverage.{md,json}`, grouped by API module. JSON includes per-input sources and whether they are user-exposed or derived/runtime-managed. Unsupported schema constructs are reported. Generation, freshness checks, and coverage all enforce complete canonical operation/input coverage. Stale API fragments, missing commands, malformed contracts, invalid mapping references, and unreadable OpenAPI fail checks. The report describes declarations; transport tests verify forwarding behavior.
