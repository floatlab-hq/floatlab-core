The evidence below pins the unchanged implementation at `c52bd3c`. Existing uncommitted documentation and release-lock edits were excluded. This assessment made no implementation changes or pushes.

**Overall: partially aligned.** There is a useful custom-rule evaluator, persistent per-resource incidents, transactional local notifications, Docker telemetry, and safe ZFS transfer machinery. RFD-0009's automatic coverage, schedule-aware execution model, inherited configuration, push delivery, incident correlation, and authenticated intervention lifecycle are not complete. Existing design documents describe intended work and are not evidence of implementation.

The refined requirements also remain incomplete: manual release discovery does not provide daily update monitoring, IPC request timing does not measure ICMP latency or packet loss, and planned scrub alerts do not establish a required scrub scheduler.

## Concrete mismatches to address

- **Unknown application health can look acceptable:** Docker inspect errors return `health = none`, the same value used for absent healthchecks; the deployment health wait accepts running containers with `none`. Preserve inspection failure as unknown. The same wait requires every listed container to be running, so an exited successful one-shot does not satisfy it. [Docker inspection](https://github.com/floatlab-hq/floatlab-core/blob/c52bd3cf4204c0a7e2d53872d4fa387e6fe3129f/pkg/docker/health.go#L60), [deployment predicate](https://github.com/floatlab-hq/floatlab-core/blob/c52bd3cf4204c0a7e2d53872d4fa387e6fe3129f/internal/worker/queue.go#L390).
- **Dashboard freshness is not enforced:** `latest()` takes the last finite value without checking its timestamp. The evaluator's freshness protection therefore does not establish freshness for displayed resource meters. [Dashboard mapping](https://github.com/floatlab-hq/floatlab-core/blob/c52bd3cf4204c0a7e2d53872d4fa387e6fe3129f/ui/src/dashboard/live.ts#L4).
- **Capacity display and collection need wiring:** the disk meter consumes allocated/size series while the storage stats handler returns a free-space series; the agent exports dataset capacity and pool I/O rather than these pool allocation/size series. Node-exporter/cAdvisor deployment and appliance startup of the separate agent metrics binary were not found in the reviewed deployment configuration. Establish end-to-end collection before claiming automatic host/storage capacity coverage. [Stats handler](https://github.com/floatlab-hq/floatlab-core/blob/c52bd3cf4204c0a7e2d53872d4fa387e6fe3129f/internal/control/routes_stats.go#L160), [meter](https://github.com/floatlab-hq/floatlab-core/blob/c52bd3cf4204c0a7e2d53872d4fa387e6fe3129f/ui/src/dashboard/live.ts#L26), [agent metrics](https://github.com/floatlab-hq/floatlab-core/blob/c52bd3cf4204c0a7e2d53872d4fa387e6fe3129f/internal/agent/metrics.go#L66), [hostd telemetry startup](https://github.com/floatlab-hq/floatlab-core/blob/c52bd3cf4204c0a7e2d53872d4fa387e6fe3129f/internal/hostd/update_telemetry.go#L34).

## Suggested delivery checklist

- [x] **Foundation:** implement agreed shared check/incident/execution/notification/intervention contracts and reconcile worker/webhook producers with the evaluator. Preserve existing history without migration or synthetic backfill.
- [ ] **Automatic coverage:** wire host/Docker/ZFS/platform signals and optional application probes to resource creation; ship reviewed defaults and inheritable overrides.
- [ ] **Host probes:** provision independent ICMP/API checks on host addition; retain probe source, latency/loss windows and thresholds, report freshness and explicit ICMP coverage gaps.
- [ ] **Platform update monitoring:** check both components on host addition and daily; persist installed/latest applicable versions, freshness and failures, deduplicate version notifications and reuse release discovery without initiating installation.
- [ ] **Required scrub scheduling:** create or adopt a trackable schedule for every managed pool, default monthly with pool overrides; prevent overlap, reconcile after restart and record confirmed completion/errors in shared execution history.
- [ ] **Protection monitoring:** persist scheduled occurrences and destination-confirmed recovery points; implement missed/overdue/restart reconciliation and independent destination history.
- [ ] **Noise control:** implement consecutive scheduled-failure policy, recovery delivery, relationship-based grouping, maintenance suppression and stale/unknown presentation.
- [ ] **Delivery:** add durable push subscriptions/outbox/attempt history and restart-safe retries; notifications remain visible without subscribers or successful delivery.
- [ ] **Intervention:** build authenticated current-state-validated requests around existing guarded operations, with stable action IDs and reconciliation of uncertain results.
- [ ] **Operator UI and limits:** complete separate health views, setting provenance, action/delivery history, unavailable-state guidance and bounded collection/retention.

The execution contract must include scrubs and pool identity alongside snapshot, replication and backup runs. Configuration and health views must expose the required scrub schedule, ICMP windows/thresholds, independent API health, and per-host component update availability with last-success times.

### Approved delivery decisions (2 November 2026)

Each checklist item's behavior and API/data changes will be reviewed before its worker implements them. Foundation is implemented and verified; later items remain subject to review.

- Pre-release development requires no migration or compatibility machinery. Do not reset existing data or fabricate historical observations, counts or execution times.
- Keep ICMP/API checks and each replication destination independent; observations retain observer identity.
- An incident represents a continuing condition, with a new incident ID on recurrence after recovery. Only fresh positive success resolves a measured condition; stale or unknown observations do not. Notification actions do not change measured health.
- Commit incident transitions and local notifications together. Preserve custom-rule timing and leave worker notification delivery unchanged until Noise control is reviewed.
- External webhook events use their supplied firing/recovery timestamps to reject out-of-order events, without an additional age cutoff. Polling checks enforce their configured freshness deadlines.
- Persist scheduled occurrences separately from retry attempts, using scheduled/running/succeeded/failed/missed/overdue states. Overdue work may still complete successfully.
- Define delivery and intervention records in Foundation; enable delivery and executable interventions only after their respective reviews.

### Foundation delivery (2 November 2026)

`pkg/monitoring` now persists producer-owned checks, attributable observations and guarded incident transitions, with incident changes and local notifications in one transaction. Metric rules, external webhooks, worker replication/pruning outcomes and host compatibility use this shared store. Custom-rule timing and explicit rule retirement remain intact; worker outcomes do not introduce new notifications.

Execution persistence distinguishes occurrences from attempts, permits late success and retains evidence of earlier missed/overdue states. Delivery and intervention types and tables establish their records without enabling push processing or executable actions. Existing historical alerts remain untouched; they are not retroactively linked to the new checks.

The full `go test ./...` suite passed with Python 3 on PATH and local fixture sockets permitted. Focused tests cover concurrent/atomic transitions, recurrence, independent destinations, ordered webhook events, observer attribution, stale/future evidence rejection, unchanged worker notification delivery and late execution success. Standards review found no actionable issues; both spec-review findings were fixed and rechecked. Live appliance, hardware and opt-in VM scenarios were not exercised. The original assessment below remains historical evidence rather than a reassessment of every checklist item.

Acceptance should demonstrate: first failure warns/second scheduled failure notifies/recovery resets; one healthy destination cannot clear another; missed start differs from overdue running work and late success; restart does not lose or duplicate incidents/deliveries/actions; stale data cannot look healthy; host outage retains child evidence without a push storm; maintenance retains history; expired/resolved/completed interventions cannot execute.

Refinement acceptance must also demonstrate:

- Host addition triggers checks for both installed components, followed by daily checks; incompatible releases are not presented as applicable updates, repeated observations of the same version do not duplicate notifications, failed discovery does not imply currency, and no update installs automatically.
- ICMP and API outcomes remain independent: ping success/API failure and ping failure/API success are visible separately. Latency and packet loss reflect the configured measurement window and source; explicitly disabling ICMP leaves a visible coverage gap.
- Every managed pool receives a monthly-default schedule or an adopted trackable schedule; pool overrides retain a schedule. Same-pool scrubs cannot overlap, restart reconciles active work, and failed/missed/overdue runs and confirmed completion/errors remain visible.

Optional cloud coordination, a cloud provider choice, forecasting and representative-workload validation are explicitly deferred or separate in the RFD, not required gaps for initial local delivery. Daily update checks and the monthly scrub default are now specified; other numerical thresholds, probe windows/intervals, budgets, retention and initial push/browser support remain product decisions.
