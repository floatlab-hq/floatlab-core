# Compact Timestamp Encoding for Snapshot Identifiers

### `FL-RFD-0008`

## Decision

FloatLab will use a **six-character, fixed-width Crockford Base32 timestamp** with a **three-second resolution** and a **2025-01-01 00:00:00 UTC epoch** for compact snapshot and backup identifiers.

The encoding will be deterministic, chronologically sortable, and easy to read, type, and communicate. It is intended primarily for ZFS snapshot naming and replication, but can be used for other short-lived operational identifiers where timestamp-level uniqueness is sufficient.

## Context and Reasoning

ZFS snapshot names are frequently used in operational commands, logs, replication bookkeeping, and manual recovery. Conventional date-based names are descriptive but lengthy; Unix timestamps are shorter but not particularly easy to communicate.

A compact timestamp should:

* Be short enough to type or dictate accurately.
* Avoid visually ambiguous characters.
* Preserve chronological order when sorting canonical strings.
* Be straightforward to encode and decode without a lookup service.
* Represent timestamps for at least a century from the chosen epoch.
* Provide enough precision for automated backups, manual snapshots, and deployment operations.

Three-second resolution offers **20 timestamp slots per minute**, with much better collision avoidance than minute-level encoding while retaining over 102 years of capacity in six Base32 characters.

## Encoding Specification

| Property | Value |
| --- | --- |
| Epoch | `2025-01-01T00:00:00Z` |
| Resolution | 3 seconds per tick |
| Encoding | Crockford Base32 |
| Alphabet | `0123456789ABCDEFGHJKMNPQRSTVWXYZ` |
| Encoded width | Exactly 6 characters |
| Tick range | `0` to `1,073,741,823` (`2^30 - 1`) |
| Timestamp slots per minute | 20 |
| Earliest representable time | `2025-01-01T00:00:00Z` |
| Last representable interval start | `2127-01-29T16:51:09Z` |
| Last representable instant | Before `2127-01-29T16:51:12Z` |
| Timezone | UTC |

The alphabet deliberately excludes `I`, `L`, `O`, and `U`. Characters are emitted in uppercase and zero-padded to six positions.

### Encoding

For a timestamp `t` expressed as an integer number of Unix seconds:

```text
epoch = 1735689600
tick  = floor((t - epoch) / 3)
value = crockford_base32(tick), left-padded with '0' to 6 characters
```

The encoder MUST reject timestamps before the epoch or at or beyond `2127-01-29T16:51:12Z`. It MUST truncate to the start of the applicable three-second interval, never round to the nearest interval. Fractional seconds, if supplied, are likewise truncated by integer interval calculation.

Digits are emitted most-significant first. No separators or checksum characters are added.

### Decoding

Decode the six-character Base32 string into its integer `tick` value and recover the start of the time interval:

```text
unix_seconds = 1735689600 + tick * 3
```

The decoded timestamp is the **interval start**, not necessarily the exact original snapshot creation time. The original second-within-interval and subsecond precision cannot be recovered.

Canonical output MUST use uppercase characters from the stated alphabet. Decoders SHOULD accept lowercase and Crockford's common transcription aliases (`O` → `0`, `I`/`L` → `1`), but MUST reject other invalid characters, including `U`. Decoder input MUST be exactly six characters long; it must not silently strip prefixes, spaces, or separators.

### Example Values

| UTC timestamp | Encoded identifier |
| --- | --- |
| `2025-01-01 00:00:00` | `000000` |
| `2026-01-01 00:00:00` | `0A0SM0` |
| `2026-10-28 00:00:00` | `0J8F40` |
| `2040-01-01 00:00:00` | `4PEMR0` |
| `2040-06-01 00:00:00` | `4TM7R0` |
| `2127-01-29 16:51:09` | `ZZZZZZ` |

For example, `2026-10-28T00:00:00Z` is 57,456,000 seconds after the epoch, or 19,152,000 three-second ticks, encoded as `0J8F40`.

## ZFS Snapshot Usage

The timestamp is an **identifier component**, not an entire snapshot naming standard. A snapshot naming scheme can combine an existing purpose-specific prefix with the identifier:

```text
pool/dataset@mzb-0J8F40
```

A backup or replication operation affecting multiple datasets SHOULD generate the identifier **once per logical operation** and reuse it across that snapshot set. This makes corresponding snapshots easy to correlate during send/receive and recovery. ZFS permits identical snapshot names on different datasets.

The identifier describes the operation's nominal timestamp bucket; it does **not** prove that snapshots on different datasets were taken atomically or at precisely the same time.

### Collision Handling

This is **not a globally unique identifier**. Two independently generated timestamps in the same three-second interval produce the same value. Two snapshots on the same dataset cannot share the same full snapshot name.

An implementation MUST handle name collisions explicitly. It MUST NOT silently overwrite, destroy, or assume ownership of an existing snapshot. Depending on the workflow, it may:

* Reuse an existing snapshot only after verifying it belongs to the same logical operation.
* Wait until the next tick and generate a new identifier.
* Reject the operation with a clear collision error.
* Use a separately specified suffix or sequence for workflows requiring multiple snapshots within one tick.

If a run identifier is shared across datasets, the collision policy MUST preserve a single identifier for that run rather than independently changing identifiers per dataset.

### Ordering

Exactly six uppercase Base32 characters with leading zeroes preserve the numeric tick order under **bytewise lexicographical comparison**. Case-folded or locale-dependent sorting is not part of the guarantee. Operational tools should continue to use ZFS metadata, such as snapshot creation time, when the exact creation order is required.

## Alternatives Considered

| Resolution | Slots per minute | Approximate six-character lifespan |
| --- | ---: | ---: |
| 1 second | 60 | 34 years |
| 2 seconds | 30 | 68 years |
| **3 seconds** | **20** | **102 years** |
| 5 seconds | 12 | 170 years |
| 10 seconds | 6 | 340 years |
| 60 seconds | 1 | 2,042 years |

**One-second resolution** is more precise but runs out of six-character values in 2059, too soon for a format intended to be stable for decades.

**Two-second resolution** lasts until 2093 but does not meet the desired century-long lifespan.

**Five- and ten-second resolutions** offer additional longevity, but enlarge the collision window without reducing identifier length.

**Three seconds** is an unusual interval, but divides a minute evenly into 20 slots and is a worthwhile compromise between precision and longevity.

## Trade-offs and Risks

* **Limited precision:** Encoded times are quantised to three-second intervals. ZFS creation metadata remains authoritative for exact creation time.
* **Collisions:** The identifier alone cannot distinguish multiple snapshots in the same interval.
* **No typo detection:** Crockford Base32 is transcription-friendly, but this six-character format has no checksum.
* **Clock dependency:** Hosts with inaccurate clocks can create misleading identifiers or move backwards in lexical order. Clock synchronisation remains an operational requirement.
* **Epoch constraint:** Historical snapshots created before 2025 cannot be encoded and require another naming scheme if imported.
* **Format longevity:** Existing identifiers MUST NOT be silently reinterpreted with a different resolution or epoch. Any future format extension requires explicit versioning or an unambiguous naming convention.

## Implementation Direction

Provide a small dependency-free Go codec with the following conceptual API:

```go
func Encode(t time.Time) (string, error)
func Decode(s string) (time.Time, error)
```

The epoch, width, alphabet, and three-second tick are constants of this format rather than runtime options. Test vectors SHOULD include the epoch, both sides of a tick boundary, the maximum representable interval, out-of-range values, lowercase and aliased input, and lexicographical ordering across Base32 digit boundaries.

The wider snapshot naming policy (prefixes, per-dataset consistency, collision retries, and any suffixes) remains separate from the timestamp codec.

## Recommendation

Adopt **six-character Crockford Base32 timestamps with three-second ticks and a 2025 UTC epoch** for new FloatLab snapshot identifiers. This gives a concise, readable representation with 20 intervals per minute and over a century of encoding capacity, while keeping the wire format and implementation simple.
