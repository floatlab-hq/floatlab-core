FL-RFD-0010: HTTPS Routing and Private Remote Access
===

**Status** Draft for discussion

## Context and Reasoning

FloatLab deploys Compose stacks on managed hosts. Published Compose ports currently bind to a stack IP, and the management API has its own administrator authentication. Operators need a way to give selected people or devices access to a service without exposing every published port or requiring a VPN for every browser visit.

Different clients need different access paths. A browser can follow an OIDC sign-in flow. A native HTTPS app may need its own sign-in or a client certificate. A Minecraft client or an SSH client needs ordinary network connectivity. Some FloatLab installations also sit behind carrier-grade NAT (CGNAT), where an operator cannot forward incoming connections at home.

## Proposal

FloatLab manages Caddy as the HTTPS router, delegates browser sign-in to an OIDC auth service, and integrates stock Headscale for private network access using the official Tailscale clients. An optional relay container on an operator-provided VPS provides public ingress for a lab behind CGNAT. The FloatLab management UI configures these components and shows their effective state.

| Example | Access | Component that enforces access |
| --- | --- | --- |
| `connect.example.net` | Public setup instructions | Caddy serves a static page with the coordination URL and enrollment steps |
| `dashboard.example.net` | Browser sign-in | Caddy asks the auth service whether the signed-in identity can access the route |
| `photos.example.net` | LAN HTTPS, overlay HTTPS, or explicitly published HTTPS | Caddy limits network reachability and applies the selected route policy. The app can handle its own login |
| `mesh.example.net` | Public coordination endpoint | Headscale handles node registration and distributes network policy |
| Minecraft on TCP 25565 | Private overlay | The Headscale policy grants access to the game endpoint. Minecraft controls which players can join |
| FloatLab management | LAN or overlay | Network access policy plus the existing FloatLab administrator login |

An operator can open the setup page from an unenrolled device, configure the alternate server in the Tailscale app, and request approval. Once approved, a guest can reach a specific game port without receiving access to the rest of the LAN. Browser users who only need a published dashboard can sign in without joining the overlay.

## HTTPS Routing and Auth

- A route names a hostname, a managed stack, a Compose service, and a container port. The operator chooses which ingress paths may serve it and how clients authenticate. New routes start private. Internet publishing is an explicit action.
- FloatLab resolves the target from the stack's active placement. Caddy receives generated configuration through a local administration endpoint. Route targets come from managed stack state. Unknown hostnames and requests arriving on an ingress where the route is disabled are rejected.
- The Pangolin-style browser flow uses Caddy forward auth and an operator-configured OIDC provider. Use an existing auth service such as OAuth2 Proxy for sign-in and sessions. FloatLab owns the per-route allow policy. The auth check must evaluate the requested route and the user's identity or configured group membership before Caddy forwards the request. Provider identity is keyed by issuer and subject. A signed-in user without a matching grant receives an access denial.
- Auth sessions use secure, HTTP-only cookies. Validate callback and return destinations against configured routes. Strip inbound identity and forwarding headers at the trusted ingress and add verified identity headers only for an upstream that explicitly needs them. Keep gateway credentials and session cookies out of workload requests. A protected route fails closed when its auth service cannot make a decision.
- An app can own authentication when its native client needs ordinary HTTPS. If published on the internet, the UI makes clear that the app handles incoming requests before it authenticates the user. A follow-up can add device-certificate mTLS at Caddy for compatible HTTPS clients. The private overlay route is available for clients that need it.
- Route creation does not implicitly publish a raw Compose port. A route presented as protected must have a backend reachable only through the configured ingress paths. Reuse the stack network where practical and verify or restrict existing published bindings that would bypass the policy. Caddy administration, control-plane peer services, and the management API have no public route by default. Gateway identity does not grant management API privileges.

[Caddy forward auth](https://caddyserver.com/docs/caddyfile/directives/forward_auth) · [Caddy configuration API](https://caddyserver.com/docs/api) · [OAuth2 Proxy integrations](https://oauth2-proxy.github.io/oauth2-proxy/next/configuration/integrations/)

## DNS and Server Certificates

- Caddy obtains and renews publicly trusted server certificates using ACME DNS-01. The operator supplies a domain and DNS credentials for a provider supported by the shipped Caddy build. Scope credentials to the smallest available DNS zone or delegate the ACME challenge records to a separate zone. Store credentials and Caddy's certificate state in protected, persistent platform storage.
- A LAN-only hostname can resolve to Caddy's private address through LAN DNS. Only the challenge TXT record needs to be visible in public DNS. For public routes, DNS points to the lab's reachable ingress or to the VPS. FloatLab shows the required DNS records and verifies them before declaring a route ready.
- Start with certificates for explicitly configured hostnames. FloatLab shows issuance, expiry, and renewal errors. Certificate failure never makes a route fall back to plaintext or removes its authentication requirement.

[Let's Encrypt DNS-01](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge) · [Caddy DNS challenge](https://caddyserver.com/docs/automatic-https#dns-challenge)

## IPv6 Overlay Addressing

- The FloatLab service overlay is IPv6-only. Each new lab generates and persists an RFC 4193 Unique Local Address (ULA) `/48` using a random 40-bit Global ID under `fd00::/8`. FloatLab uses the first `/56` of that allocation for its service overlay, leaving the rest of the `/48` reserved. IPAM allocates up to 256 `/64` subnets within the `/56`. Joined nodes use their lab's existing allocation. Recovery of the same lab preserves it, while an independent lab created from a copy gets a new one.
- Independently generated prefixes make collisions unlikely. Before activating a cross-lab share, compare the participating lab prefixes and reject overlap. Advertise only the service routes an operator has approved. Use a `/128` where the service has a dedicated address and enforce allowed protocols and ports separately.
- Keep FloatLab service addresses separate from Headscale node addresses. Stock Tailscale clients expect node addresses within `fd7a:115c:a1e0::/48` for IPv6. Advertise FloatLab ULA service addresses through approved subnet routes instead of assigning them as Tailscale node addresses. Verify IPv6-only overlay operation with the supported stock clients.
- The overlay's address family does not constrain the transport underneath it. A client may connect over an IPv4-only internet connection. Workloads that currently bind only to IPv4 can use an IPv6 service endpoint backed by a local proxy, with no change to the workload's existing IPv4 address.

[RFC 4193 addressing and collision probability](https://www.rfc-editor.org/rfc/rfc4193.html#section-3) · [Headscale node address ranges](https://headscale.net/stable/about/faq/#how-can-i-migrate-back-to-the-recommended-ip-prefixes) · [Headscale subnet routes](https://headscale.net/stable/ref/routes/)

## Headscale and Private Services

- Run stock Headscale as a managed system service when private remote access is enabled. Use its API for device approval, revocation, and access policy. The public coordination hostname has a dedicated Caddy route that preserves the Tailscale control protocol upgrade and uses Headscale's registration flow.
- Apply an explicit deny-by-default policy before enrolling devices. Publish only the IPv6 routes needed for enrolled clients to reach selected service endpoints or the private HTTPS listener. Restrict each grant to the intended identity, destination, protocol, and port. A guest must not inherit access to other workloads or lab management.
- The public setup page contains instructions and the coordination URL. Registration requires operator approval or an expiring, single-use enrollment key delivered privately. Device revocation and policy changes are visible in FloatLab. The UI distinguishes a control service outage from a failure to reach a particular workload.
- Use the configured DERP map for fallback when peers cannot connect directly. A self-hosted DERP server can be configured separately if needed. Headscale does not carry application traffic through its coordination endpoint. The official Tailscale app still activates one network at a time, and clients that cannot install it need another device to route on their behalf.

[Headscale registration](https://headscale.net/stable/ref/registration/) · [Policy](https://headscale.net/stable/ref/policy/) · [DERP](https://headscale.net/stable/ref/derp/) · [Tailscale custom coordination server setup](https://tailscale.com/docs/how-to/set-up-custom-coordination-server)

## Follow-up — Sharing Services Between Labs

Labs under one administration can use one Headscale instance with grants that distinguish the labs and their services. Independently administered labs keep their own Headscale instances. Headscale does not federate those instances, so FloatLab would coordinate explicit service shares between them.

- The exporting operator chooses a service and approves a connector identity for the receiving lab. The export grants that connector access to a specific endpoint, protocol, and port. The receiving operator accepts the share and selects which local users or devices may use it.
- A connector in the receiving lab runs two isolated overlay identities. It listens on a service endpoint in its own overlay and opens the upstream connection through its identity in the exporting lab. Separate userspace Tailscale nodes are a candidate implementation. The service proxy keeps each Headscale address space separate even when its node addresses overlap. The distinct FloatLab ULA prefixes also allow a later routed design to carry specific service addresses across a lab-to-lab link.
- For example, Lab A shares its Minecraft TCP port with Lab B. A player in Lab B enters Lab B's private address for the imported service and stays signed in to Lab B's tailnet. Lab A sees the connector identity at the network layer and delegates local client access decisions to Lab B. Minecraft can still authenticate and allowlist individual players.
- Each share is directional and can be revoked by either operator. The exporter enforces revocation at its own network boundary. The importer removes or disables the local endpoint. FloatLab shares selected workload endpoints and disallows re-exporting imported endpoints through its sharing interface. Each lab retains its own device registration, policy, and workload ownership.
- A first proof should share one TCP service between two labs with different ULA prefixes whose Headscale node ranges and home IPv4 subnets overlap. Verify that an authorized local client stays on its own tailnet, other ports remain unreachable, and exporter-side revocation blocks new connections even if the importer leaves its endpoint configured. Attempt a share with a duplicate lab prefix and verify that it is rejected.

[Headscale federation discussion](https://github.com/juanfont/headscale/issues/1370) · [Tailscale userspace node API](https://tailscale.com/docs/reference/tsnet-server-api)

## Optional VPS Relay for CGNAT

With direct ingress, public DNS points at the lab and the operator forwards HTTPS to Caddy. With relay ingress, public DNS points at the VPS and the lab opens a WireGuard connection from inside its network. This relay is separate from the client overlay. An HTTPS visitor does not need a phone-side VPN to use it.

```text
Browser or Tailscale client
    → public VPS TCP 443
    → WireGuard link to the lab
    → Caddy
    → authorized HTTPS route or Headscale coordination endpoint
```

- FloatLab generates a lab-side connector configuration and a companion container configuration for a Linux VPS the operator controls. Pair the endpoints using WireGuard public keys. The lab maintains the outbound path through NAT. The VPS forwards raw TCP 443 only to a dedicated Caddy listener over the link.
- Caddy terminates TLS in the lab. The VPS holds no app TLS keys, DNS credentials, or Headscale administration credentials. Restrict the relay peer and host firewall to the dedicated ingress listener so the VPS cannot reach LAN services, raw game ports, or the management plane through this link. Caddy applies the same internet publishing policy to direct and relayed requests.
- The initial relay supports TCP HTTPS, including the Headscale control upgrade. UDP forwarding, including HTTP/3 and public game ports, is outside this relay's initial scope. A TCP proxy without source address forwarding makes relayed requests appear to come from the VPS. Access checks rely on authenticated identities. A relay failure leaves LAN access available and is reported as a remote ingress outage. The UI shows the last WireGuard handshake and a separate end-to-end ingress check.

[WireGuard configuration and NAT keepalives](https://www.wireguard.com/quickstart/) · [Headscale reverse proxy requirements](https://headscale.net/stable/ref/integration/reverse-proxy/)

## Management and Failure Handling

- Add a Remote Access view to the existing management UI. Show routes by stack, their reachability and auth policy, DNS and TLS status, device enrollment and access grants, and relay health. Keep a local recovery path through the existing management login if remote ingress or the identity provider is down.
- FloatLab stores desired configuration and reports what Caddy, Headscale, and the relay have actually applied. Validate before activation. A failed update may leave a previously valid route running, but a route requested disabled or made more restrictive must be closed if the new restriction cannot be applied. Status must expose pending changes and failures.
- Treat the ingress node as an explicit placement in the first release. Resolve workloads through their current authorized placement. If a workload moves or is unavailable, reconcile its upstream when the new target is verified or report it unavailable. This proposal does not add automatic failover for Caddy, Headscale, or the VPS.
- Audit route publication, policy edits, device approval and revocation, and relay pairing. Keep private keys, enrollment keys, and DNS credentials out of logs. Reuse the monitoring and notification model in [RFD-0009](rfd-0009.md) for persistent failures.

## Acceptance Checks

Extend the existing Compose and multi-node integration scenarios to exercise the management API and real client traffic through the configured ingress.

1. A LAN-only hostname gets and renews a trusted certificate with DNS-01 while internet clients cannot reach the route.
2. For an OIDC route, a permitted browser session succeeds. An unauthenticated request, a signed-in user without a grant, and a request with forged identity headers are denied. An unavailable auth service denies access. A client cannot bypass the policy by dialing the stack's port directly.
3. An official Tailscale client on an IPv4-only internet connection enrolls against the custom coordination server. Over the IPv6 overlay, a guest can reach the granted Minecraft port but cannot reach a second workload or management. Revoking that device blocks new connections.
4. With inbound access to the lab blocked, an internet client reaches an approved HTTPS route and can enroll through Headscale via the VPS. Requests for private hostnames and attempts to reach other ports over the relay are blocked.
5. A route update, stack move, or component restart leaves observed state accurate and preserves the route's access policy. A relay outage leaves the LAN route usable.

## Initial Scope and Open Questions

Start with one lab ingress node, one supported DNS provider, one OIDC provider per lab, stock Headscale, and one optional VPS relay. Defer cross-lab service sharing, automated client certificate enrollment and renewal, public game relaying, custom client apps, and ingress high availability.

Before implementation, choose the first DNS provider and auth service configuration, and confirm the host firewall mechanism for already-published ports. Decide whether FloatLab should ship a default DERP map or ask the operator to configure one during setup.
