FL-RFD-0009: Platform Monitoring and Notifications
===

## Context and Reasoning

FloatLab needs to automatically monitor the infrastructure and operations it manages. Operators should be able to see whether hosts and workloads are available, storage is healthy, and scheduled snapshots, replication, and backups are completing.

Monitoring should be created as part of configuring a host or workload. Users should not need to separately recreate checks for resources and schedules FloatLab already knows about.

FloatLab should ship with sensible defaults intended to work without adjustment for approximately 95% of workloads. Users can change installation defaults and override individual checks, thresholds, and notification behavior to suit their services. Validation of default coverage across representative workloads will be handled separately.

This RFD defines monitoring coverage, incident handling, notifications, and operator intervention. It builds on RFD-0006: Metrics and RFD-0007: Log Aggregation, following the Compose deployment and host-pinning model described in RFD-0003 and RFD-0004.

## Automatically Created Checks

### Host Availability and Docker

When a host is added, FloatLab will monitor:

- Host reachability.
- Freshness of host health reports.
- Docker Engine availability.
- Available memory, CPU pressure, and filesystem capacity.
- OOM kills and unexpected Docker service failures.

Host reachability, host reporting, and Docker availability will be shown separately. A host may respond to ping while Docker is unavailable, or continue running workloads while its management connection is interrupted.

### Workload and Container Health

When a Compose workload is deployed, FloatLab will monitor:

- Whether containers expected to be running are running.
- Docker healthcheck results, where defined.
- Unexpected exits and repeated restarts.
- Deployment completion and whether containers reached their required state.

One-shot containers will be evaluated by their expected completion result. Intentional shutdowns and containers outside the active deployment should not generate availability failures.

FloatLab will automatically use healthchecks supplied by the workload. Where none exist, the interface will show that application health has not been verified.

Users can add HTTP, TCP, or application-specific checks and configure their expected results. A running container alone does not establish that the application is working.

### ZFS Storage Health

For managed ZFS pools and workload datasets, FloatLab will monitor:

- Pool state.
- Device read, write, and checksum errors.
- Scrub results and overdue scrubs where a schedule exists.
- Pool free space and workload dataset quota usage.
- Whether required datasets are present and mounted.

Storage degradation will remain visible even when workloads continue operating successfully.

### Snapshot Jobs

When a snapshot schedule is configured, FloatLab will monitor:

- Scheduled execution and successful completion.
- Failed, missed, or overdue executions.
- Whether the expected snapshot exists.
- Retention cleanup failures.

Starting the scheduler or snapshot process will not count as successful completion.

### ZFS Replication

When replication is configured, FloatLab will create monitoring for each source and destination relationship.

Each relationship will track:

- Source and destination availability.
- Scheduled execution and successful ZFS send/receive completion.
- The last successfully received snapshot.
- Failed, missed, or overdue transfers.
- Transfer duration and available destination capacity.

A successful transfer to one destination must not hide a failure to another.

By default, the first failed or missed attempt will appear as a warning in the interface. A second consecutive failed or missed attempt will notify the operator.

### Backup Jobs

When a backup destination and schedule are configured, FloatLab will monitor:

- Destination reachability.
- Scheduled execution and successful completion at the destination.
- Failed, missed, or overdue jobs.
- Available destination capacity, where inspectable.
- Retention cleanup failures.

Each destination will have its own result and history. Restore verification will only be reported where a verification operation has actually run.

### Platform Services

FloatLab will monitor its own node services, including:

- Host management.
- Snapshot, replication, and backup scheduling.
- Metrics and log collection.
- Notification delivery.

Service failures and stale information will appear in the control plane while it remains available.

## Defaults and Configuration

FloatLab will provide installation-wide monitoring defaults. Individual workloads can override them, with host and storage settings configurable at their relevant resource.

Configurable settings will include:

- Check frequency and timeout.
- Consecutive failures required before notification.
- Resource warning and critical thresholds.
- Job start grace periods and maximum expected duration.
- Application startup grace periods.
- Notification severity and delivery preferences.
- Additional application checks and their expected results.

The interface will show the effective setting and whether it comes from an installation default or an explicit override. Users can return an overridden setting to the installation default.

Changes to installation defaults will apply to resources that inherit them. Explicit overrides will remain in place.

Initial capacity monitoring will use configurable thresholds with clear units. More advanced handling, such as predicting when a pool will fill, can follow separately.

## Health and Incident Model

FloatLab will use one incident model to evaluate signals from host reports, Docker, ZFS operations, application checks, and metrics rules.

The model will distinguish:
| Record | Purpose |
| --- | --- |
| Check result | What was observed, when, and from where |
| Incident | A continuing condition requiring attention |
| Notification | A delivery attempt informing an operator |
| Intervention request | A request for an operator to choose a corrective action |


Multiple observations can contribute to one incident. For example, a container exit and a failed application check may describe the same workload failure.

Related incidents will be grouped using known resource relationships. If a host becomes unreachable, FloatLab should avoid sending a separate push notification for every workload it can no longer inspect. The individual observations will remain available.

Simultaneous failures alone will not establish a shared cause.

Acknowledgement, notification delivery, and incident resolution are separate states. Acknowledging an incident will not mark its checks healthy.

## Scheduled Operation Tracking

Each snapshot, replication, and backup execution will have a unique identifier and record:

- Scheduled time.
- Start time.
- Completion time.
- Result and failure reason.
- Relevant source, destination, workload, and host.

Execution states will distinguish:
| State | Meaning |
| --- | --- |
| Scheduled | Waiting for its execution time |
| Running | Started and has not completed |
| Succeeded | Completed and its result was confirmed |
| Failed | Returned a failure |
| Missed | Did not start within its allowed grace period |
| Overdue | Started but exceeded its expected duration |


An overdue operation may still complete successfully. Its status should show whether it remains active and when progress was last observed.

After a service restart, FloatLab will reconcile unfinished execution records against the actual operation and destination state before retrying.

## Failure Handling

For host reachability and scheduled ZFS replication, the default behavior will be:

1. Record and display the first failed check or missed execution.
2. Notify after a second consecutive failure.
3. Clear the consecutive failure count after success.
4. Send a recovery notification if the incident previously generated a notification.

For replication, the second failure means the next scheduled attempt also fails or is missed. Alert evaluation will not launch an additional transfer.

The interface will show the current failure count and next expected check or execution. Users can override the default failure allowance.

Confirmed faults, such as an unavailable ZFS pool or an OOM kill, will use event-appropriate notification rules rather than automatically inheriting the missed-ping policy.

Maintenance, intentional shutdowns, and deployment startup periods will suppress expected notifications while retaining history.

## Health Presentation

The control plane will show separate health information for:

- Hosts and Docker Engine.
- Workloads and containers.
- ZFS pools and datasets.
- Snapshot jobs.
- Each replication relationship.
- Each backup destination.
- Platform services.

A workload can be available while replication or backups are failing. These conditions will remain individually visible.

Every check will show its current result, failure reason, last observation, last success, and associated incident.

Missing observations will become stale or unknown. An old successful result will not continue to appear as current health.

## Notifications and Operator Intervention

### PWA Push

The preferred notification interface is a FloatLab PWA installed on a phone or desktop.

A notification service running in a container on the node will connect to a push service and deliver updates to subscribed devices. It will restart automatically, preserve subscriptions and pending delivery state, and retry failed deliveries.

Notifications will identify the affected resource, explain the condition, and link to the relevant control plane view.

### Persistent Incident and Delivery State

Incident changes and pending notification deliveries will be committed together to persistent storage.

After a restart, the notification service will resume pending work. Stable incident, notification, and action identifiers will allow repeated delivery attempts to be recognized without creating duplicate incidents.

Corrective actions will recheck current state and existing execution records before proceeding. An uncertain action result must be reconciled before another attempt is made.

Local persistence protects against container restarts. It does not provide notification coverage for complete node or storage failure.

### Intervention Requests

For the initial version, FloatLab will ask the operator for direction when additional corrective action is required. Existing Docker restart policies will continue operating independently.

If automatic correction is introduced later, actions with material risk will continue to require operator direction.

Intervention requests will explain:

- What failed and the current impact.
- Available actions and their consequences.
- Required checks or prerequisites.
- Whether the request is still current.

Push notifications will open an authenticated intervention view. Before executing an action, FloatLab will revalidate the condition, operator permissions, and relevant prerequisites.

Expired, resolved, or previously completed requests must not execute against outdated state.

### Initial Intervention Actions

| Action | Required behavior |
| --- | --- |
| Retry a failed snapshot | Recheck storage availability and prevent overlapping execution |
| Retry failed replication | Recheck both endpoints and existing transfer state |
| Retry a failed backup | Recheck the destination and existing execution |
| Restart a container or workload | Identify affected containers and expected interruption |
| Redeploy the current workload definition | Show the definition being applied and expected impact |
| Begin manual fail-over | Open the fail-over workflow with its required safety checks |


Acknowledgement, notification muting, and maintenance mode will also be available as incident-management actions.

Storage repair, snapshot rollback, and backup restoration will remain in their dedicated workflows.

### Control Plane Unavailability

Receiving a push notification does not guarantee an intervention can currently be executed.

If the control plane or responsible host is unavailable, the PWA will show the last known condition, its observation time, and manual guidance. Executable actions will remain unavailable until FloatLab can validate the current state.

### Notification and Action History

The control plane will retain:

- Failure and recovery events.
- First and most recent occurrence.
- Affected resources.
- Delivery attempts and their results.
- Acknowledgements and intervention requests.
- The operator’s chosen action and its outcome.

Notifications will remain in this history even when push delivery fails or no device is subscribed.

## Collection Efficiency

FloatLab will reuse existing host reports, Docker events, metrics, and job execution results wherever possible.

Additional probes will be created only when they provide information not already available. Resource relationships will also prevent duplicate checks against shared infrastructure.

Collection concurrency, check frequency, and history retention will be bounded to suit resource-constrained hosts. Monitoring should not introduce competing polling loops for the same information.

## Observer Failure and Optional Cloud Coordination

Detecting the complete loss of the monitoring node is a separate capability.

Where an installation uses a cloud quorum node, it could independently detect that local monitoring is unavailable. Optional cloud coordination could also retain incident summaries and intervention requests during a local outage.

A durable state model, such as Cloudflare Durable Objects or an equivalent, is a possible implementation for that optional service. This RFD does not select a cloud provider or make cloud connectivity a requirement for local monitoring.

An operator response received while the installation is disconnected will remain a request. An authorized local executor must reconnect and revalidate it before taking action.

## Initial Delivery Scope

- Automatic host, Docker, container, and ZFS monitoring.
- Snapshot, replication, and backup execution tracking.
- Installation defaults and individual resource overrides.
- Sensible thresholds and transient failure handling.
- Optional application checks.
- One incident model with related-failure grouping.
- Persistent local incident and notification delivery state.
- PWA push notifications and authenticated intervention requests.
- Notification and action history.
- Maintenance suppression and explicit stale or unknown states.
- Reuse of existing signals with bounded collection and retention.

## Outstanding Questions

- What resource budget should monitoring, notifications, and retained history consume on each node?
- Which numerical thresholds, intervals, and grace periods should ship as defaults?
- Which PWA push delivery mechanism and browser combinations should initial delivery support?
- What retention periods should apply to check results, incidents, and action history?
- Should optional cloud coordination use Durable Objects or another persistent coordination service?
- Should a surviving host provide an intervention interface when the primary control plane is unavailable?
