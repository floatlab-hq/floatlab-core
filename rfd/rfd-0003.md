# Workload Hosting

### `FL-RFD-0003`

FloatLab will host workloads in Containers, using the open-source Docker tooling. FloatLab will expose each workload via
the web admin interface as a `docker-compose.yml` file that can be deployed to a specific host, and fail-over to a
nominated host.

FloatLab will not be operating as a cluster, see [RFD-0004](./rfd-0004.md) for more details

FloatLab will assist the user in creating, and editing `docker-compose.yml` files, by both providing an editor that
can validate the file, assist in configuring volumes, editing ENV variables, injecting sidecars and assigning networks. FloatLab will store
FloatLab-specific deployment metadata directly in the compose file using `x-fl-*` extension fields, including:

- Snapshot schedule
- Primary host
- Secondary host, replication schedule, and failover priority
- Backup destination and schedule

**Reasons for basic workload definitions in `docker-compose.yml`:**

- Single configuration file for each workload
- Very common for projects to publish example `docker-compose.yml` saving the user from having to translate the config
- Contains enough configuration to deploy nearly any workload
- Does not contain complicated features like auto-scaling, auto-placement, or other complex orchestration logic
- Allows for multiple containers in a single "stack"
**Reasons against using `docker-compose.yml`:**

- `docker-compose.yml` is not a standard format, and is not portable between different orchestrators
- `docker-compose.yml` has no support for adding additional configuration required by FloatLab

We see this as a fair trade-off compared to using docker swarm, kubernetes, or helm-charts for workload deployment. All of which require unique definitions and are less portable than a standard docker-compose.yml that can work on any machine running docker.

### Deployment & Control Plane Options

The following options were considered for workload hosting and operations control:

#### Option A: Docker Engine + `docker-compose.yml` + FloatLab `x-fl-*` extension metadata (**Recommended**)

- Workload definition remains user-facing and portable via `docker-compose.yml`
- FloatLab-specific behavior is captured in explicit `x-fl-*` extension fields in the same file
- Suitable for single-host and warm-standby/failover patterns without introducing cluster complexity
- Lowest operational overhead for target user profile and current product phase

#### Option B: Docker Swarm

- Adds built-in scheduler and service abstraction
- Requires translating user expectations from plain compose behavior into swarm semantics
- Introduces additional control-plane operations burden with limited alignment to current requirements

#### Option C: Kubernetes (direct manifests or Helm)

- Highest flexibility and ecosystem support
- Substantially higher complexity in platform operation, packaging, and user support
- Poor fit for current goals focused on straightforward, portable, non-cluster deployments

#### Option D: Separate companion file for FloatLab metadata

- Separates metadata from workload definition but introduces dual-file operational complexity
- Increases drift risk between runtime config and policy config
- Adds import/export and lifecycle overhead compared to a single compose artifact

#### Decision Criteria

- User portability of workload definitions
- Operational simplicity for both user and FloatLab
- Clear, predictable namespacing of platform policy config inside compose (`x-fl-*`)
- Ability to support backup/replication/failover in non-cluster mode
- Future migration path to more advanced orchestration if required

#### Automatic Workload Image Upgrades

Docker Compose remains the source of truth for workload images and their upgrade policies. Each registry-backed service can set `x-fl-auto-upgrade` in Compose or use the workload's **Upgrade images** tab. The policy applies to all containers for that service. Existing and new services inherit Patch when the setting is omitted.

| Policy | Eligible updates for a service running `2.13.3` |
| --- | --- |
| Disabled | Keep the current image and report the highest newer stable release in the same image variant. |
| Patch | Highest newer stable `2.13.x` release. |
| Minor | Highest newer stable `2.x.y` release. |
| Major | Highest newer stable release. |

Versioned services stay in the same repository and variant, such as `-alpine`. A named tag such as `stable` stays on its publisher's channel even when a numbered tag points to the same image. Patch, Minor and Major follow a changed digest on that channel because a named tag cannot establish the scope of a release. Disabled services on a named tag report the digest change as an available upgrade. [Workload image alerts](rfd-0009.md#workload-image-upgrade-alerts)

##### Saving and Pinning Images

On create, Compose edit, or start with a submitted Compose project, the primary appliance looks up registry-backed image references. This applies even when automatic deployment is Disabled. FloatLab resolves `latest`, implicit tags, and partial version tags to the most specific matching full version it can find in the same repository. The replacement must have the same registry manifest digest. A resolved reference takes the form `repository:tag@sha256:<digest>`. The tag gives operators a readable version or channel and the digest selects the exact artifact.

If an equivalent full version cannot be verified for a floating tag, FloatLab keeps the tag, pins the digest when available, and returns a warning. If the digest lookup fails or rewriting an indirect Compose value would change how it is resolved, the save retains the submitted reference and returns a warning. Services built from Compose source are outside registry pinning and automatic upgrades. FloatLab tracks the pins it created so the scheduler can advance them. Explicit digest pins supplied by an operator stay fixed. A fixed pin with a tracking tag can still report available upgrades.

Saving a Compose edit stores the definition for its next deployment. The save response includes the definition with any resolved pins. The dashboard and CLI editor supply the previously loaded definition so a concurrent deployment or edit cannot be overwritten by a stale draft.

##### Scheduling and Eligibility

The lab shares one daily maintenance window, initially **02:30–03:30**, which each workload's primary appliance interprets in its configured local timezone. Operators can read and update it via `GET` and `PUT /api/v1/settings/workload-upgrades`. A new automatic upgrade must start before the window closes. A rollout or rollback already underway can continue past the end. A missed window waits for the next scheduled day.

The scheduler checks running workloads against their deployed images and Compose configuration. It can establish a baseline for an older stack from the running image's registry digest. It starts an upgrade only on the primary appliance when the stack is healthy, the saved Compose configuration matches the running deployment, and the stack has no competing operation. Docker healthchecks must pass when present. For services without them, the scheduler can verify that the containers are running. Changes to the saved configuration or workload state after admission can defer the operation before it starts.

##### Rollout, Recovery, and Retry

Eligible services in one stack upgrade together in a single recorded operation. FloatLab pulls the candidate images by digest, takes a recursive pre-upgrade ZFS snapshot of the workload, saves the candidate Compose definition, and reconciles the stack. The operation succeeds when the stack passes its existing health gate within the configured timeout.

If deployment or health verification fails, FloatLab stops the failed deployment, restores the snapshotted ZFS data and the previous Compose configuration with the exact prior image digests, and checks the restored stack's health. Writes made after the snapshot are discarded by the restore. A failure before snapshot creation leaves the old deployment serving. A completed failure raises an alert even when rollback succeeds, and a failed rollback is recorded separately. [Failure alert behavior](rfd-0009.md#workload-image-upgrade-alerts)

FloatLab records failed automatic candidates across restarts. It skips the same candidate set or a subset of a failed set during later windows, so dropping a service from a batch or republishing the same numbered version does not trigger an automatic retry. For a named channel, the candidate identity includes the digest. A different eligible release or channel digest can make a later batch eligible again. Operators can still initiate a manual upgrade. Failure records accompany a stack move and are carried into a same-stack takeover when available in the source replica.

The single-node ZFS appliance regression test observes `1.0.1` overwrite workload data before failing its health check. It verifies that rollback restores the exact `1.0.0` image and the original data and raises an active failure alert. It then advances the guest clock across daily windows to verify that `1.0.1` is skipped and that `1.0.2` installs successfully with the restored data intact. [Appliance regression test](../integration/workload_upgrade_test.go)

### Minimum Delivery Scope (MVP)

The minimum scope required for initial release:

- Compose authoring/validation with policy checks
- Deployment to primary host with tracked state
- Secondary host designation with manual failover
- Snapshot + backup scheduling with restore capability
- Basic secrets injection and encrypted storage
- Core observability (status, logs, critical alerts)

### Post-MVP Hardening

- Automatic failover with configurable safeguards
- Secret rotation workflows and enhanced audit controls
- Backup integrity automation and regular restore validation
- Expanded governance controls (approvals, policy packs)
- Compatibility tooling for schema evolution across releases

### Secrets Management

Each workload will allow for the storage of secrets with-in the workload volume. These can be imported into the
workload using the `docker-compose.yml` file.

### Sidecar Configuration Alternative

FloatLab-specific operational metadata should be represented using `x-fl-*` extension fields in `docker-compose.yml`,
rather than overloading container labels intended for runtime/container discovery concerns.

### Volume Management

Float lab will automatically create a volume for each workload, and a sub-volume for each container volume mount. These
can have additional settings (eg Disk Quote, Block Size, Compression). These volume paths will be automatically
translated into the correct paths, and validated after manual file editing.

### Network Management
Each container will automatically receive a unique IP address rather than the default of sharing the host's IP. This will reduce the contention for port numbers, reduce the need for reverse proxies and help simplify the migration of containers to different hosts.
