# Installer developer guide

Run the Bubble Tea installer locally with its mock service to develop the UI and
exercise installation flows. Mock mode uses simulated disks and progress, requires
no root privileges or ZFS tools, and exits when you choose Reboot.

## Requirements

Use a Linux development environment, Go 1.25.5 or newer, and an interactive
terminal. Run the commands below from the repository root, where `go.mod` lives. Go downloads dependencies on the first
build when they are not already cached.

## Preview the ISO display in a local VM

With Docker Desktop running, launch from the repository root:

```bash
./scripts/dev-installer-vm.sh
```

Open [the local VM viewer](http://127.0.0.1:6080/vnc.html?autoconnect=1&resize=scale).
The browser displays the guest's actual framebuffer; its own font and the Mac
terminal font do not affect rendering. Use the viewer's scaling setting for a
pixel-for-pixel view or to fit the screen into your window.

The x86-64 NixOS VM and production ISO import the same
`nixos/modules/installer-display.nix`: kmscon, Pango software rendering, IBM Plex
Mono at 16 pixels, a round-dot FloatLab Braille fallback, and Unifont for other Unicode characters.
The Braille font is generated by `scripts/generate-braille-font.py` with FontTools.
Both use the appliance flake's pinned Nixpkgs revision. The preview uses a
1600×1000 virtual display and the mock service; no installation disks are attached.
On Apple Silicon the guest is emulated, so the initial boot is slower than the
ordinary Docker TUI. Subsequent UI edits do not require rebooting the VM.

After editing the TUI, run `./scripts/dev-installer-vm.sh` again. It rebuilds the
Linux binaries and restarts the preview display service through the QEMU guest agent. After
changing the Nix display or font configuration, stop the VM before relaunching:

```bash
./scripts/dev-installer-vm.sh --stop
./scripts/dev-installer-vm.sh
```

Source, mock binaries, logs, and screenshots stay in this checkout under
`.local/installer/vm/`. The Nix build cache uses the Docker-managed Linux volume
`floatlab-installer-nix`, because Nix requires Linux filesystem permissions.
The container is `floatlab-installer-vm`; its viewer is bound to localhost only.
Stop it with `./scripts/dev-installer-vm.sh --stop` when finished.

## Run mock mode with Go

### macOS with Docker Desktop

Start Docker Desktop, then run from the repository root:

```bash
./scripts/dev-installer.sh
```

This runs the Linux mock installer in an ephemeral container. Source files stay
in this checkout; compiled binaries and Go caches stay under `.local/installer/`
(ignored by Git). Docker manages the Go image in its own image storage. No host
disks or Docker socket are mounted into the container, and no privileged mode is
used.

Edit `internal/installtui/`, stop the preview container from another terminal, and run the same command again.
Each launch rebuilds both binaries using the cached dependencies and build output.
Scenario and timing flags pass through to the TUI:

```bash
./scripts/dev-installer.sh --scenario rejected-config --step-delay 100ms
```

### Linux with Go

Build the mock service, then run the TUI directly from source:

```bash
go build -o /tmp/floatlab-install-service-mock ./cmd/install-service-mock
go run ./cmd/install-tui --mock --service /tmp/floatlab-install-service-mock
```

The TUI launches the service as a separate process. Pass `--service` explicitly
with `go run`, because Go places the temporary TUI executable in its own build
directory. The `--mock` flag forwards mock scenario and timing options to the
service.

After editing the TUI, run the second command again. After editing the installer
service, rebuild the mock service with the first command before rerunning the TUI.

## Choose a mock scenario

For example, reject the first configuration submission and run the simulation
faster:

```bash
go run ./cmd/install-tui --mock \
  --service /tmp/floatlab-install-service-mock \
  --scenario rejected-config --step-delay 100ms
```

| Scenario | Behavior |
| --- | --- |
| `success` | Completes after valid configuration is submitted. This is the default. |
| `delayed-config` | Adds a delay before the configuration phase. |
| `rejected-config` | Rejects the first configuration submission; allows correction and resubmission. |
| `failure` | Fails halfway through the simulated image copy. |
| `cancellation` | Reports simulated frontend loss and cleanup as a terminal failure. |

`--step-delay` controls the time between simulated progress updates. The success
screen still uses a 30-second reboot countdown. Mock pool dry-runs always succeed;
command parsing and host, network, and account validation still run.

## Walk through the UI

1. Disk selection opens automatically. Select disks with Space and move with the arrow keys.
   The installer creates one pool, `floatlab`; selecting multiple disks generates
   a mirror within that pool.
2. Choose Next to preview the generated ZFS layout. The unboxed command has a
   Customise zpool action directly below it to open the complete command editor. In the editor, Enter inserts
   a newline; Ctrl+S validates and opens the preview. Choose Erase All and continue
   to confirm the simulated disk layout. No typed confirmation is required.
3. Enter host settings. Open the timezone list with Enter and type to filter it.
   Select DHCP or Static with Left/Right or Space. Static address fields appear
   only for Static. Select Next to validate network settings before account
   setup opens.
4. Set up the administrator account. Empty or mismatched passwords and invalid
   usernames remain on this screen until corrected. The strength meter updates as
   you type. Choose TOTP Yes/No on the same screen with Left/Right or Space.
   If enabled, scan the compact, theme-colored QR or use the manual secret.
   Verify the authenticator code on that screen, then save the recovery codes.
   Review the validated configuration before submitting it.
5. Watch the compact progress footer. Success starts the automatic reboot countdown;
   choose Reboot to reboot immediately. Mock reboot exits the installer. Failures
   remain visible until you choose Reboot.

Back/Next actions sit two blank lines below the content. Unavailable Back actions
are hidden. The contextual help bar sits one row above the bottom. Up/Down or Tab/Shift+Tab move between fields and the action row. In the
action row, Left/Right choose Back or Next, Enter or Space activates the selected
action, and Up returns to editing. In the command editor, Down from its last line
reaches the actions; Enter still inserts a newline. Esc also goes Back.

Back preserves edited settings. It is hidden after disk confirmation when
installation is already running, and after configuration has been submitted.
Waiting screens disable navigation; completed and failed installs offer Reboot.
Alt+Up/Down scroll the main area.

The installer uses Everfloat exclusively. The focused controls, main background,
progress indicator and help bar all use that palette. Wider terminals center the content in an 84-column
area with aligned field/value tables. Taller terminals also show the FloatLab
logo and FloatLab Installer title at the left of that column. Compact consoles retain stacked fields and automatic scrolling.

Use the Reboot button or Ctrl+R after completion or failure. There are no quit or
pause shortcuts. Ctrl+C and Ctrl+D are ignored by the TUI.

## Build standalone executables

Build both executables into the same directory so the TUI can find its mock service
without `--service`:

```bash
go build -o /tmp/floatlab-installer/ ./cmd/install-tui ./cmd/install-service-mock
/tmp/floatlab-installer/install-tui --mock
```

## Run development checks

```bash
go test -race ./internal/installer ./internal/installtui
go vet ./internal/installer ./internal/installtui ./cmd/install-tui ./cmd/install-service ./cmd/install-service-mock
go build ./cmd/install-tui ./cmd/install-service ./cmd/install-service-mock
```

The tests cover command parsing and disk mapping, configuration validation,
service lifecycle, UI choices, progress, and reboot behavior.

## Find the implementation

| Location | Responsibility |
| --- | --- |
| `internal/installtui` | Screens, keyboard handling, timezone choices, and progress display. |
| `internal/installer/service.go` | Stdio JSON protocol, validation, session state, and mock scenarios. |
| `internal/installer/storage.go` | Disk discovery, partition layout, and ZFS command parsing. |
| `internal/installer/worker.go` | Real installation, verified EFI copying, and configuration. |
| `internal/installer/os.go` | Root archive validation, version snapshot installation, and current clone creation. |

For ISO builds and tests against disposable VM disks, see the
[appliance README](README.md#build-the-iso). Changes to dependency versions or imported dependency packages require
updating `vendorHash` in `floatlab-appliance-image/flake.nix` before building the ISO.
